# 这门课怎么上

这是 MiniCodex 的学习计划。`AGENTS.md` 是给 Codex 的纪律，`docs/COLLAB.md` 是我们俩的工作流程，
这份文件只回答一件事：**接下来几个月，按什么顺序、用什么节奏，把 codex 的核心手写一遍。**

先说清楚要造的是什么。不是"一个能用的 codex"，而是九个能编译、能测试、你能讲清楚的模块。
代码大部分由 Codex 打字，但结构你定、语义你判断、测试你验收。所以判断进度的标准不是"跑起来了"，
而是"你能不看代码说清这一段在干什么"。

## 一、你会拿到什么

三个阶段结束后，你手上会有：

- `crates/` 下九个 crate，每个 300–1500 行，覆盖从协议类型到前端输出的完整链路；
- `docs/modules/` 下每个模块一份路书，写的是"先读哪、再写什么、怎么验"，不是 API 手册；
- 一个能跑的最小 agent：给它一句话，它会请求模型、执行命令、改文件、把过程打成 JSON 行。

比这些更重要的是：你能解释 `Op` 为什么不能序列化、工具结果为什么必须进历史、
一次 turn 为什么是一个循环而不是一次请求。这三件事答不上来，代码写完了也等于没学。

## 二、为什么先跑通一条细线

按 crate 排课（先类型、再配置、再执行……）看起来整齐，实际很难受：前十个小时你看不到任何会动的东西，
而且类型是先验的——背下了 `ResponseItem`，却不知道它在第几步被谁构造。

所以顺序改成 tracer bullet：先用一条最细的线把"一轮对话"跑通，再逐段把假件换成真件。

| 段 | 干什么 | 跑通后你会看到 |
|----|--------|----------------|
| R0 | workspace 骨架 + `x.sh` | `./x.sh` 绿（已完成） |
| R1 | 最小类型子集：三个 ID、四个条目、六个事件 | 手写一段 JSON，能解成事件再编码回去，`type` 是 `task_started` |
| R2 | 假模型 + 单轮循环 | 终端依次打出 `task_started`、`agent_message`、`task_complete` |
| R3 | 一个 `shell` 工具，工具回环 | 中间多出 `exec_command_begin/end`，`call_id` 能对上 |
| R4 | `apply_patch`，失败不留半成品 | 上下文不匹配时文件没变，事件里是错误 |
| R5 | 配置分层 + `AGENTS.md` 注入 | 往仓库根加一行指令，请求内容跟着变 |
| R6 | JSONL 落盘与恢复 | 杀掉进程再启动，能接着上次的会话 |
| R7 | 真模型：SSE、重试、usage | 换掉假客户端，事件流的形状不变 |
| R8 | 前端收口：`--json`、`-o`、退出码 | `mc-cli --json` 每一行都是合法 JSON |

这个顺序不是偏好，是被代码结构逼出来的。`run_turn` 的骨架决定了后面每个部件被调用的位置，
所以 R2 必须早于任何细节——没有循环，类型和工具都没有落脚点。工具输出会进入历史、进而进入下一轮请求，
所以 R3/R4 要在 R5（上下文）之前，你才会亲眼看到"为什么历史里要存工具输出"。
真模型的 SSE 是最脏的一段，放在最后，出错时你能分清是循环写错了还是解析写错了。

旧的 M1–M8 编号没有废：它对应 crate 名和文档名。R 是施工顺序，M 是模块编号，两者是映射关系，不是两套课程。

## 三、每个阶段你具体做什么

每个阶段都遵循同一个循环，四次专注时间足够：

1. 读路书里指的那几段上游代码（通常 100–200 行），把不懂的地方记下来；
2. 写笔记三行：这段在链路里的位置、它的输入输出、最容易误解的一点；
3. 按路书的步骤写代码，每步之后跑 `./x.sh`，绿了再继续；
4. 补测试，然后回答路书末尾的验收问题。

卡住的时候分两种情况处理：语义不清楚，就让我派 Codex 去读那一段并解释（它只讲行为，不贴代码）；
编译或测试不会调，直接把错误贴给 Codex，让它指出问题在哪，实现仍然你自己写。

## 四、我们三个怎么分工

你负责决定"这段我到底懂没懂"，以及写代码。这是唯一不能被代劳的部分。

我（Hermes）负责写派单、核对 Codex 的结论、把结果写成路书、在你说"过了"的时候做最后验收。
我不会把 Codex 的原话直接贴给你——它的结论只有在我用源码逐条核实之后才会进入文档。

Codex 负责读代码。它的上下文比我们大，不怕枯燥，适合把 6800 行的 `protocol.rs` 按区间读成一份结构化报告。
但它会复述注释、会把"看起来像"说成"就是"，所以它的产出永远只是草稿。

## 五、路书长什么样

每份路书都按同一个骨架写，读起来像一篇说明文，不是字段清单：

- 开头一段说清这个模块在链路的哪个位置、它坏掉会影响谁；
- 然后是"上游在哪"，给出具体文件和行号区间，按阅读顺序排；
- 接着讲数据结构，只讲我们要做的那部分，并明确说清哪些不做；
- 再讲语义：不变量、顺序、错误路径，每条都带出处；
- 然后是测试清单（每个模块十到十二条，含错误路径和边界）、手写步骤、常见误解、验收问题。

步骤按"每步不超过一百行、每步结束都能编译"切。这一步做不完，说明模块切大了，回头拆。

## 六、节奏

一个阶段两到四次专注时间，每次一到两小时。九段加起来六到八千行代码，按每周两三次估，八到十周。

派单的额度纪律：一次只问一个模块的一个问题域。"帮我看看 protocol 里都有什么"这种问题会得到一份
看起来很有道理、但大部分没有出处的报告；换成"这三个类型在中断场景下的行为差异，逐条给 path:line"，
才有用。

## 八、第一块的边界（用来校准后面的颗粒度）

上游 `protocol` crate 有三万四千行、七十多个模块。我们只做会话内核，四个文件：

`ids` 照抄三个 ID（`SessionId`、`ThreadId`、`ResponseItemId`），因为它们的 serde 是手写的，正好学一遍。
`items` 只做 `ResponseItem` 的五种变体（消息、推理、函数调用、函数输出、未知兜底）和两种 `ContentItem`。
`turn` 只做四种 `TurnItem`，注意它的 tag 是 PascalCase，和 `ResponseItem` 相反。
`event` 只做六个事件，注意 `TurnStarted` 上线时叫 `task_started`。
`op` 只做 `TurnInput` 和 `Interrupt`，并且**不给它加 serde**——上游的 `Op` 带 `oneshot::Sender`，本来就不能序列化。

不做的部分：realtime、MCP、hooks、guardian、permissions、计划模式、图片、记忆、插件。
判断标准只有一句：**M7 的单轮循环用不到的，就不做。**
