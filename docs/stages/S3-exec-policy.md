# S3 命令前缀策略与审批

当模型申请执行 `touch 'my file'` 时，用户需要知道它准备创建哪个文件，工具也需要按同样的参数运行。S3 在 S2 的 Shell 工具前放置一个 `PolicyGuard`。向注册表登记这个包装器后，`shell` 的公开参数变为 `{"command":"touch 'my file'"}`。注册表仍然调用同一个 `Tool` 接口。

## 分词后再作决定

`split_command` 识别空白分隔的参数和成对的单双引号。引号内可以包含空格，空引号保留一个空参数。相邻的引号片段可组成同一个参数。在引号内，另一种引号是普通字符。其他字符按字面值处理。缺少程序名返回 `EmptyCommand`，未闭合的引号返回带引号字符的 `UnclosedQuote`。

`ExecPolicy::evaluate` 把非空规则前缀与 `argv` 起始位置的完整参数比较。例如规则 `["git", "status"]` 能覆盖额外参数 `--short`，而单独的 `["git"]` 长度不足，`status-extra` 也是另一个参数。空前缀跳过。所有匹配项共同决定结果，规则顺序和前缀长短都不能让放行覆盖拒绝。

| 规则匹配结果 | 决策 | 执行前的动作 |
|---|---|---|
| 有拒绝规则 | `Deny { reason }` | 立即向模型返回原因 |
| 有放行规则，且所有匹配项均允许放行或询问 | `Allow` | 直接执行 |
| 其余情况 | `Ask` | 把参数切片交给审批回调，同意后才执行 |

前缀规则的作用范围是程序名及其开头的参数。批准一个能够自行解释脚本的程序时，策略授予的是相应程序能力。编写具体规则时，应按实际需要选择程序和参数前缀。

## 把审批和执行接在同一条路径上

`PolicyGuard::call` 是第三处练习。它取得 JSON 中的 `command`，只分词一次。分词失败直接返回错误，遇到 `Deny` 或审批拒绝时，在启动进程前结束。获准时按 S2 的 `{"argv":[...]}` 契约转交刚刚评估过的参数，让带空格的一个文件名始终只占一个参数。直接执行这一组参数也保留了引号内标点的字面值。

`ApprovalHandler` 的输入是借用切片，返回值只表示本次请求是否同意。闭包适配器让测试可以记录回调次数，在同意之前检查文件状态，也能检测本应直接决定的路径是否意外弹出了审批。

骨架与行为样例见 [policy.rs](../../src/policy.rs) 和 [s3_exec_policy.rs](../../tests/s3_exec_policy.rs)。

## 验收与复核

```bash
./x.sh s3
```

9 个同步用例覆盖普通分词、引号与空参数、词法错误、按参数匹配、两种顺序下的拒绝优先级，以及放行、批准、审批拒绝、规则拒绝四条执行路径。执行用例会调用 S2 的 ShellTool，按学习顺序先完成 S2。最后两个用例在临时目录内检查文件确实没有创建。复核时追踪一次批准请求，指出哪一组参数被匹配、被用户看到、被交给操作系统。
