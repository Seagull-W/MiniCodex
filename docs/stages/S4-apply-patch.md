# S4 文件编辑与原子补丁

模型想同时修改接口和调用方时，两个文件必须先通过上下文检查。如果接口文件先写回，随后才发现调用方已经被别人改过，工作区就会留下半次重构。S4 把一批文件编辑作为一次工具调用，由调用方提供可信的工作目录。

## 补丁文本怎么读

下面的补丁新增说明、调整版本，再删除旧标记文件。示例中三项操作共用一个根目录。开始前，`version.txt` 的内容为 `1\n`，`old-flag` 已存在。

```text
ADD notes.txt
CONTENT "升级到第二版\n"
UPDATE version.txt
SEARCH "1\n"
REPLACE "2\n"
DELETE old-flag
```

操作头占一行，关键字后的一个空格分隔路径，余下整段是相对路径。操作体也按行读取。每个 `CONTENT`、`SEARCH`、`REPLACE` 后面都是一个 JSON 字符串，所以能精确区分文件末尾有无换行，也能表示引号、空行及形似关键字的正文。补丁最后一行可带换行。

| 操作 | 后续行 | 对文件的要求 |
|---|---|---|
| `ADD path` | 恰好一个 `CONTENT`，允许空字符串 | 父目录已存在，目标尚不存在 |
| `UPDATE path` | 一对或多对 `SEARCH` 与 `REPLACE` | 文件已存在，每个非空搜索串在该步内容中恰好匹配一次。空替换表示删除该段 |
| `DELETE path` | 无 | 文件已存在 |

一个补丁至少有一个操作，每个文件只出现一次。同文件的多处修改写入同一个 `UPDATE`，按 hunk 顺序使用上一个 hunk 的结果。保留搜索串以外的原始字节，包括行尾。语法错误的行号从 1 开始。

## 实现时要守住的边界

1. **解析只处理文本。** `parse_patch` 生成按输入排序的 `Patch`。例如 `REPLACE new` 缺少 JSON 字符串的双引号，应报告这一行的 `PatchError::Syntax`。此时无需访问文件系统。
2. **预检面对公开的构造类型。** `apply_patch_atomic` 也能收到调用方直接构造的 `Patch`。它要检查每个路径和每个操作。在本练习中，文件路径必须由根下的普通相对路径分量组成，绝对路径、`..`、经过符号链接的路径均拒绝。检查新增文件时也要检查祖先目录。为每个文件保留原貌，并在内存中计算最终内容。把上下文缺失和多处匹配分别报给模型，两种情况需要模型补充不同信息。
3. **整批通过后才写盘。** 首文件预检成功，次文件匹配失败时，所有文件应逐字节保留原貌。写盘阶段将准备好的结果逐个提交，完成后汇总新增、修改、删除的文件数。提交途中遇到可恢复的 I/O 错误时，利用保留的原貌回退已提交的文件，并报告原始错误。如果回退也失败，错误信息须同时指出回退失败的路径和原因。预检失败的验收使用独占的临时工作区。并发进程修改文件、进程崩溃或断电后的跨文件恢复，均超出这项测试的保证范围。
4. **连接模型与文件接口。** `ApplyPatchTool::call` 从 `{"patch": "..."}` 取出字符串，在构造时绑定的根目录下应用补丁，把文件数摘要或错误原因交给 S1 的工具结果通道。S2 完成后可将它作为普通工具注册。

```rust
let mut registry = ToolRegistry::new();
registry.register(Box::new(ApplyPatchTool::new(project_root)));
```
